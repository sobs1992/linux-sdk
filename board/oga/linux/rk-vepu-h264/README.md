# rk-vepu-h264: аппаратный кодер H.264 Rockchip VEPU2 (PX30/RK3326)

Драйвер V4L2 mem2mem (stateful-кодер) для кодера VPU в PX30. В mainline этим
блоком управляет hantro, но только как JPEG-кодером; H.264 на нём умеет лишь
библиотека Rockchip MPP через их собственный драйвер. Модуль собирается как
внешний (`LINUX_EXT_MODULES` в `configs/oga_defconfig`), ставится в
`/lib/modules/<версия>/updates/` и грузится сам по узлу VPU
(`rockchip,px30-vpu`). Hantro в ядре OGA выключен (`board/oga/linux/oga.config`),
потому что он берёт тот же узел. Устройство — `/dev/videoN` с именем драйвера
`rk-vepu-h264`.

| Очередь | Форматы |
|---|---|
| OUTPUT (кадры) | `XR24` (V4L2 XBGR32 = DRM XRGB8888, в памяти B,G,R,X) — кодер сам переводит RGB в YUV BT.601 полного диапазона; `NV12` (одна плоскость, Y, затем UV, строки по 16 пикселей) |
| CAPTURE | `H264`: Annex B, Constrained Baseline (CAVLC), один срез на кадр; перед каждым IDR — SPS и PPS |

Размеры 96×96…1920×1088, чётные. Ширина и высота, не кратные 16, кодируются
целыми макроблоками, а в SPS пишется `frame_cropping`. В VUI указаны полный
диапазон (для RGB) и `max_num_reorder_frames = 0`: декодер показывает каждый
кадр сразу. Управление: `V4L2_CID_MPEG_VIDEO_BITRATE`, `GOP_SIZE`,
`FRAME_RC_ENABLE`, `H264_I_FRAME_QP`/`P_FRAME_QP` (без RC), `H264_MIN_QP`/`MAX_QP`,
`FORCE_KEY_FRAME`; частота кадров — `VIDIOC_S_PARM`. RC — как в meson-venc: один
QP на кадр по размерам прошлых кадров; цель P-кадров — `битрейт/fps`, IDR — вчетверо больше.

Параметр модуля `debug=1`: в журнал ядра пишется каждый кадр (тип, QP, байты, время).

## Проверка

`test/venc-test.c` (копия теста meson-venc) — синтетические кадры: полосы и
движущийся квадрат, с `-p 1` — с шумом. Результат пишется в `.h264`:

```sh
output/oga/buildroot/host/bin/aarch64-buildroot-linux-gnu-gcc -O2 -o venc-test \
    board/oga/linux/rk-vepu-h264/test/venc-test.c
# на плате (bare_app держит устройство, пока трансляция включена):
venc-test -f XR24 -s 960x640 -n 300 -b 3000000 -p 1 /tmp/out.h264
# на ПК:
ffmpeg -err_detect explode -i out.h264 -f null -
```

Проверено на ODROID-GO Advance BE (2026-11-13):

- **Время на кадр.** 960×640 — 8–9 мс, 480×320 — ~2 мс.
- **Битрейт держится.** При цели 3 Мбит/с получилось 3007 кбит/с, при цели 4 Мбит/с — 3999.
- **Чистота потоков.** 3000 кадров подряд без единой ошибки; `-err_detect explode` ошибок не находит.
- **Цвета.** Полосы совпадают с исходными в пределах ±2.
- **Нестандартные размеры и входы.** 854×480 (обрезка в SPS) и NV12 работают.
- **Переполнение.** Переполнение выходного буфера (`BUFFER_FULL`) даёт ошибку кадра; следующий кадр — IDR с QP выше.
- **В bare_app.** Стрим Heroes III 960×640 идёт на 30 кадрах/с, bare_app занимает ~10% CPU. С OpenH264 было 19 кадров/с при ~35%.

## Как устроено

Кодер сам переводит RGB в YUV, ищет движение по одному опорному кадру и пишет
срез вместе с заголовком: `frame_num`, `idr_pic_id`, QP, параметры фильтра берёт
из регистров. Поэтому SPS и PPS драйвера должны с ним совпадать:
`log2_max_frame_num = 16`, `pic_order_cnt_type = 2`,
`deblocking_filter_control_present = 1`, `pic_init_qp = 26`. SPS и PPS драйвер
пишет в начало буфера CAPTURE. Кодер продолжает поток с последнего 8-байтного
слова заголовков: недописанные байты передаются в `STR_HDR_REM_MSB/LSB`, их
длина в битах — в `STREAM_START_OFFSET`. Лимит потока задаётся в 64-битных
словах, а после кадра в том же регистре лежит длина в битах. Реконструкции —
два буфера NV12 по макроблокам (Y, затем UV); после каждого кадра они меняются
местами. Перед стартом в регистр `ENCODE_START` сначала пишется только формат
H.264 (от него зависит смысл остальных регистров), потом все 184 регистра,
потом старт. Конец кадра — прерывание `vepu`; сторожевой таймер 500 мс
сбрасывает зависший кодер.

Что писать в регистры, взято из Rockchip MPP (`mpp/hal/vpu/h264e`,
`hal_h264e_vepu2_v2.c`, Apache-2.0): настройки кадра, таблицы штрафов по QP,
коэффициенты RGB→YUV. Имена регистров — из `rockchip_vpu2_regs.h` hantro
(копия: `vepu2_regs.h`, GPL-2.0). Питание и часы — через runtime PM (домен
`PX30_PD_VPU`, IOMMU `vpu_mmu`), ACLK 300 МГц, как у hantro.

## Чего нет

- **CABAC (Main profile).** Нужна таблица контекстов в памяти, это ~10–15% битрейта.
- **Поблочный RC по контрольным точкам кодера.** Регистры `CHECKPOINT`; сейчас один QP на кадр.
- **Нулевое копирование входа (DMABUF из bare_app).** Очередь DMABUF уже принимает.
