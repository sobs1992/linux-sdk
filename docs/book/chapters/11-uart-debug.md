# Отладка: «прошил, вставил — ничего не происходит»

Первый образ OGA собрался, прошёл все проверки из главы 10 и был записан на карту.
Консоль включили — экран чёрный, горят только красные светодиоды. Эта глава —
подробный разбор того, как от этого симптома дойти до причины. Методика важнее
результата: она пригодится на любой плате.

## Шаг 1. Получить UART

Без последовательной консоли отладка загрузчика — гадание. У OGA есть разъём UART
(TX, RX, GND на торце, 3,3 В). Адаптер USB-UART подключается к ПК:

```bash
ls -l /dev/ttyUSB*                  # crw-rw---- root dialout ... /dev/ttyUSB0
id | grep dialout                   # пользователь должен быть в группе dialout
lsusb | grep -i -E 'cp210|ch34|ftdi|pl23'
lsusb -v -d 10c4:ea60 | grep iProduct    # → CP2102 USB to UART Bridge Controller
```

!!! warning "Ловушка: модель адаптера имеет значение"
    Классический **CP2102** умеет максимум **921600 бод**. Rockchip любит 1 500 000.
    CP2102N, CP2104, FT232R, CH340 умеют 1,5–3 Мбод. Модель видна в `lsusb -v`.

## Шаг 2. Порт занят

```text
$ stty -F /dev/ttyUSB0 115200 raw
stty: Device or resource busy
$ fuser -v /dev/ttyUSB0
/dev/ttyUSB0:  sobs  696728 F.... screen
$ screen -ls
	696728.pts-2.sobs-pc	(Detached)
```

Порт держала **отсоединённая** сессия `screen`, запущенная командой
`screen /dev/ttyUSB0` — **без указания скорости**. Без скорости `screen` открывает
порт на 9600 бод, а загрузка печатает на 115200: на экране был бы мусор или ничего.

!!! tip "Как снять содержимое чужой сессии screen"
    `screen -S <pid> -X hardcopy -h файл` сохраняет экран и историю прокрутки
    в файл, не трогая сессию. Здесь он показал пустоту — подтверждение, что на 9600
    ничего полезного не пришло. Правильный запуск: `screen /dev/ttyUSB0 115200`,
    выход — `Ctrl-A`, `K`.

## Шаг 3. Записать загрузку в файл

Глазами быстрый поток не прочитать, а мусор не скопировать. Пишем порт в файл
**до** включения платы:

```bash
stty -F /dev/ttyUSB0 115200 raw -echo cs8 -cstopb -parenb -crtscts
timeout 180 cat /dev/ttyUSB0 > boot.log      # включаем плату, ждём
wc -c boot.log
cat -v boot.log | head                        # непечатные байты как ^X и M-x
```

`raw` выключает всю обработку символов терминалом, `cs8 -cstopb -parenb` — формат
8N1, `-crtscts` — без аппаратного управления потоком. Перед захватом полезно
отправить Enter (`printf '\r\n' > /dev/ttyUSB0`): если плата уже висит в U-Boot или
Linux, придёт приглашение.

## Шаг 4. Читать мусор

Захват на 115200 при включении:

```text
68 байт
^@^@^@^@M-xSM-{.M-{M-g6M-oM-:M-nM-^[M-^?&M-~wM-/M-~M-^MM-^ZM-#Q^K...
```

Четыре нулевых байта в начале — переходный процесс на линии TX при включении
питания. Дальше — **мусор**. Мусор — это не «ничего»: плата что-то передаёт, но на
другой скорости. Какой?

### Оценка скорости по мусору

Когда приёмник медленнее передатчика, он видит «старт-бит» на любом переходе в
ноль, а остальные биты выбирает редко — получаются байты, в которых много единиц
(`0xFF`, `0xFE`, `0xF8`…). Именно такие байты в захвате (`M-x` = `0xF8`, `M-{` = `0xFB`,
`M-~` = `0xFE`). Значит, источник **быстрее** 115200.

Порядок величины можно оценить. Если источник передаёт на скорости `S`, а приёмник
настроен на `R < S`, то один принятый «байт» (10 бит на скорости `R`) покрывает
примерно `S/R` переданных байтов. Для 1 500 000 / 115 200 ≈ 13:

```text
68 принятых байт × 13 ≈ 880 байт, переданных на 1,5 Мбод
```

Затем запись на «1 500 000». CP2102 такую скорость не умеет; драйвер `cp210x`
ограничивает скорость максимумом модели, так что реально порт, по-видимому,
работал на 921 600 (`stty` при этом молча «соглашается» на 1 500 000). Получили
707 байт мусора. Пересчёт: 1 500 000 / 921 600 ≈ 1,63, 707 × 1,63 ≈ 1150 байт.

Две независимые оценки сходятся: **около 1 КиБ текста на ≈ 1,5 Мбод**.

!!! note "Это грубая оценка"
    Она предполагает непрерывный поток и ничего не говорит о содержимом. Но для
    гипотез её достаточно: «быстро» против «медленно» и «полстраницы» против
    «трёх строк».

## Шаг 5. Что должно было печататься

Что напечатал бы наш загрузчик? Смотрим код, а не гадаем:

```bash
grep -n -E 'printascii|printf' src/u-boot/drivers/ram/rockchip/sdram_px30.c
#   715:	printascii("out\n");          ← TPL после инициализации DDR
```

TPL после инициализации DDR печатает `out`, SPL — баннер `U-Boot SPL 2026.07 (...)`.
Оба — на `CONFIG_BAUDRATE` = 115200 через debug UART, тактируемый от 24 МГц
(`board_debug_uart_init()` в `px30.c`). В захвате на 115200 нет ни одного читаемого
символа. Вывод: **наш TPL вообще не запускается**. А ≈ 1 КиБ на 1,5 Мбод — это
типичный лог DDR-блоба и miniloader из rkbin Rockchip (`DDR Version ...`,
`Boot1 Release Time ...`, `SdmmcInit ...`).

## Шаг 6. Исключить очевидное

Прежде чем строить сложные гипотезы, проверяем простое: а на карте точно наш образ?

```bash
lsblk -o NAME,SIZE,FSTYPE,LABEL,PARTUUID /dev/sda
#  sda1 128M vfat BOOT   4f474131-01
#  sda2 363M ext4 rootfs 4f474131-02         ← таблица разделов наша
cmp /run/media/$USER/BOOT/Image output/oga/linux-install/Image && echo "Image OK"
sudo dd if=/dev/sda bs=512 skip=64 count=18496 status=none \
  | cmp - output/oga/images/u-boot-rockchip.bin && echo BOOTLOADER OK
```

Всё совпало: и разделы, и ядро, и загрузчик по сектору 64.

## Шаг 7. Индикатор без UART

Ещё одна проверка без всякого UART: у U-Boot OGA в DTS стоит

```dts
&blue_led { default-state = "on"; };      /* rk3326-odroid-go2-u-boot.dtsi */
```

Если U-Boot proper стартует, загорается **синий** светодиод. Он не горел — до U-Boot
дело не доходило. Это сходится с шагом 5.

!!! tip "Совет"
    Ищите в DTS для U-Boot (`*-u-boot.dtsi`) светодиоды с `default-state`, подсветку,
    вибромотор — всё, что меняет видимое состояние платы. Это бесплатный индикатор
    «до какой стадии дошли».

## Шаг 8. Кто печатает на 1,5 Мбод?

Если наш код с SD не стартует, но кто-то печатает лог загрузчика Rockchip — значит,
BootROM нашёл загрузчик **где-то ещё**. На плате есть SPI-флеш: в DTS OGA есть
узел `jedec,spi-nor`. А BootROM RK3326 проверяет SPI **раньше** SD.

Во SPI-флеш ничего не писали. Но в наработках лежал форк U-Boot от Hardkernel, и
в нём нашлись два очень говорящих файла:

```bash
$ ls sd_fuse/
boot.ini  idbloader.img  rk3326_header_miniloader_spiboot.img  sd_fusing.sh  ...
$ strings -n 6 sd_fuse/rk3326_header_miniloader_spiboot.img | head
EFI PART
...
DDR Version 1.12 20190528
```

И скрипт `build_recovery.sh`:

```bash
pack_spi_full_image() {
  dd if=rk3326_header_miniloader_spiboot.img of=spi_recovery.img seek=0 count=2048
  dd if=uboot_spi.img of=spi_recovery.img seek=2048 count=2048
  dd if=trust_spi.img of=spi_recovery.img seek=4096 count=4096
  # + dtb и картинки: logo_hardkernel, low_battery, no_sdcard, recovery ...
}
```

Hardkernel собирает **образ для SPI-флеша**: DDR-блоб + miniloader + свой U-Boot +
картинки «нет SD-карты», «низкий заряд». У Black Edition этот recovery-загрузчик
**стоит во SPI с завода**. Картина сложилась:

1. BootROM находит загрузчик во SPI и запускает его (DDR-блоб + miniloader печатают
   ≈ 1 КиБ на 1,5 Мбод — это наш мусор).
2. Miniloader видит SD-карту и пытается загрузить с неё `uboot.img` (сектор 16384) и
   `trust.img` (сектор 24576) **в формате Rockchip**.
3. По сектору 16384 на нашей карте лежит mainline-FIT `u-boot.itb`, а не `uboot.img`.
   Miniloader его не принимает и зависает. Горят только красные светодиоды.
4. Старая карта EmuELEC/Hardkernel работала именно потому, что на ней `uboot.img`
   и `trust.img` лежали в формате Rockchip по этим секторам.

!!! note "Подтверждение"
    Окончательно гипотезу подтвердил гибридный образ (глава 12): как только на карте
    появился `uboot.img` в формате Rockchip, консоль загрузилась. Ещё один простой
    тест, который стоит знать: включить плату **без SD-карты**. Если мусор на 1,5 Мбод
    тот же — загрузчик живёт во SPI/eMMC.

## Варианты решения

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| Стереть заголовок SPI | бэкап `sf read` → `fatwrite`, затем `sf erase 0 0x100000` | полностью mainline, всё на SD | меняет заводскую прошивку; карта не загрузится на стоковой консоли |
| Mainline U-Boot во SPI | `u-boot-rockchip-spi.bin` | быстро | загрузчик уходит из образа; сломанный SPI-загрузчик сложно восстановить |
| `uboot.img`/`trust.img` в формате Rockchip на SD | `loaderimage`, `trust_merger` | SPI не трогаем; работает на любой стоковой BE | начало цепочки — блобы Rockchip |
| **Гибрид** | и mainline idbloader, и RK-формат на одной карте | работает и со SPI, и без него | чуть сложнее разметка |

Выбран гибрид — глава 12.

!!! danger "Если всё же трогать SPI"
    Всегда сначала бэкап: в U-Boot консоли `sf probe`, `sf read 0x02000000 0 0x1000000`,
    `fatwrite mmc 1:1 0x02000000 spi-backup.bin 0x1000000` — и проверить файл на ПК
    (`strings` должен показать `EFI PART` и `DDR Version`). Стирайте только заголовок
    (`sf erase 0 0x100000`), а не весь флеш. Если записать во SPI валидный, но
    зависающий загрузчик, BootROM будет запускать его вместо SD, и восстанавливать
    придётся через режим MaskROM по USB.

## Методика в сжатом виде

1. **Получить данные**: UART в файл, с момента включения, на нужной скорости.
2. **Читать мусор**: мусор значит «не та скорость»; характер байтов говорит, быстрее
   или медленнее; количество — порядок объёма.
3. **Знать, что должно быть**: найти в коде, что и на какой скорости печатает каждая
   стадия.
4. **Исключить очевидное**: на карте то, что вы думаете? `cmp` по секторам.
5. **Искать побочные индикаторы**: светодиоды, подсветка, USB-устройства в `lsusb`.
6. **Читать чужой код**: вендорские скрипты (`build_recovery.sh`) рассказывают про
   железо больше, чем документация.
7. **Проверять гипотезу минимальным изменением**: тест без SD, один новый файл на
   карте.
