# Ошибки и уроки

Ошибки по дороге — нормальная часть работы. Важно, чтобы они быстро обнаруживались
и не повторялись. Здесь собраны все промахи, сделанные при построении SDK, — с
симптомом, причиной и уроком. Многие из них типичны и встретятся вам самим.

## Нехватка памяти: OOM убил графическую сессию

**Симптом.** Посреди сборки трёх новых плат IDE закрылась, все фоновые сборки исчезли.

**Причина.** Одновременно шли три сборки Buildroot (каждая собирала GCC в 17 потоков)
и сборка ядра в 16 потоков — около 70 тяжёлых процессов компилятора на машине с
14 ГБ ОЗУ. Средняя нагрузка доходила до 100. Журнал ядра:

```text
kernel: systemd invoked oom-killer: ...
kernel: Out of memory: Killed process 5485 (gvfsd-metadata) ...
systemd[4422]: org.gnome.Shell@ubuntu.service: Failed with result 'oom-kill'.
```

OOM killer убил GNOME Shell, с ним закрылись сеанс, IDE и все дочерние процессы.

**Как найти.** `journalctl -k --since "20:50" | grep -i -E 'out of memory|oom'` и
`uptime` (средняя нагрузка за 5 и 15 минут).

**Урок.** Параллельность должна учитывать память, а не только ядра. GCC при сборке
самого себя может требовать до 1 ГБ на процесс. На 14 ГБ — одна сборка Buildroot
за раз. Make и Buildroot продолжают с места остановки, поэтому повторный запуск
ничего не потерял.

## `pkill -f` убил собственную команду

**Симптом.** Команда остановить медленный `git clone` и подставить зеркало
завершилась с кодом 144, половина действий не выполнилась.

**Причина.** `pkill -f 'git clone https://source.denx.de/...'` ищет шаблон в **полной
командной строке** процессов. Строка оболочки, которая выполняла `pkill`, тоже
содержала этот текст — `pkill` убил свою же оболочку.

**Урок.** Убивать по PID (`pgrep -a`, затем `kill <pid>`) или делать шаблон, который
не совпадёт с вашей командой (`pkill -f '[g]it clone'` — классический трюк).

## `cd` в несуществующий каталог

**Симптом.** Файлы BR2_EXTERNAL оказались в `src/`, а не в `board/oga/buildroot/`.

**Причина.** `cd board/oga/buildroot && ...` — каталога ещё не было. `cd` упал,
но следующие команды были через `;`, а не через `&&`, и выполнились в текущем
каталоге.

**Урок.** Сначала `mkdir -p`, потом `cd`. Связывайте команды через `&&` или включайте
`set -e`. После массового создания файлов — `find` и проверить, где они оказались.

## `unexport FW` создал пустую переменную

**Симптом.** `make info` после `make oga_defconfig` говорил «No firmware config
selected».

**Причина.** `unexport FW` перед `FW ?= $(shell cat ...)` определяет переменную `FW`
пустой; `?=` после этого ничего не присваивает.

**Как найти.** `make -p info | grep -B2 '^FW :*='` — make сам показывает, в какой
строке определена переменная.

**Урок.** `make -p` (база данных переменных и правил) — главный инструмент отладки
Makefile.

## `git mv -k` молча ничего не сделал

**Симптом.** `rmdir blobs` — «Directory not empty», файл остался на месте.

**Причина.** Файл ещё не был добавлен в git. `git mv` такие файлы не трогает, а `-k`
подавляет ошибку. Код возврата — 0, поэтому запасной `|| mv ...` тоже не сработал.

**Урок.** Ключи вида «игнорировать ошибки» прячут проблему. Для неотслеживаемых
файлов — обычный `mv`.

## `[ ... ] && x` в конце цикла под `set -e`

**Симптом.** Потенциальный: `mkimage.sh` мог молча завершиться при пустом `IMAGE_RAW`.

**Причина.** Код возврата цикла `while` — код возврата его последней команды. Если
последняя команда — `[ -n "$x" ] && put ...` и условие ложно, цикл вернёт 1, и
`set -e` завершит скрипт.

**Урок.** Под `set -e` используйте `if ...; then ...; fi` вместо `cond && action`,
особенно в конце функций и циклов.

## Забытый `chmod +x`

**Симптом.** `make: scripts/fetch-files.sh: Permission denied`, цепочка сборки
RPi остановилась.

**Урок.** Новые скрипты сразу делать исполняемыми. Git хранит бит исполнения, так что
после `git add` его будет видно в `git diff` как `new file mode 100755`.

## Опции Kconfig, которые не включились

Два случая — панель OGA (`BACKLIGHT_CLASS_DEVICE=m`) и VC4 на Pi 4 (`SOUND=m`) —
разобраны в главах 2, 8 и 13. Урок: **всегда проверять итоговый `.config`** против
фрагмента. Для этого в SDK есть `kconfig-check.sh`.

## Параметр ядра, который ни на что не влиял

**Симптом.** Пользователь хотел перевернуть экран OGA, поменял `fbcon=rotate:3` на
`fbcon=rotate:0`, пересобрал, прошил — ничего не изменилось.

**Причина.** `CONFIG_FRAMEBUFFER_CONSOLE_ROTATION` в arm64 `defconfig` выключен, и без
него ядро игнорирует `fbcon=rotate:` целиком. Параметр был скопирован из командной
строки Hardkernel без проверки, что поддержка собрана. Консоль всё время была в
родной ориентации панели; заметили это только когда попытались её поменять.

**Как найти.** Убедиться, что изменение дошло до карты (`extlinux.conf` в образе), а
затем найти, кто читает параметр: `grep -n initial_rotation
drivers/video/fbdev/core/fbcon.c` — код под `#ifdef CONFIG_FRAMEBUFFER_CONSOLE_ROTATION`.

Попутно выяснилось, что подсказка из DTS (`rotation = <270>` → `rotate:1`) даёт
перевёрнутую картинку, а правильное значение — исходное `rotate:3`.

**Урок.** Параметр командной строки — это тоже код, который может быть не собран.
Для каждого нестандартного параметра проверяйте, какая опция Kconfig его включает.
И проверяйте, что изменение **видно** на железе, а не только что оно есть в конфиге.

## Файл, удалённый из overlay, остался в rootfs

**Симптом.** В rootfs два файла: `profile.d/oga.sh` и `profile.d/sdk.sh`.

**Причина.** Buildroot копирует overlay в `target/` и никогда не удаляет из `target/`.

**Урок.** После переименований и удалений в overlay — `rootfs-clean` или ручное
удаление из `output/<fw>/buildroot/target/`.

## Захват UART мешал работать с консолью

**Симптом.** После загрузки нельзя было ввести команду в консоли UART.

**Причина.** Фоновый `cat /dev/ttyUSB0` продолжал читать порт. Два процесса,
читающие один tty, делят входящие данные между собой случайным образом.

**Урок.** Захват — с ограничением по времени (`timeout`), и останавливать его, когда
он больше не нужен.

## Неполная первая гипотеза

**Симптом.** Раскладка карты была исправлена, а образ всё равно не грузился.

**Причина.** Гипотеза «дело в смещениях» объясняла прошлые неудачи, но не учитывала
загрузчик во SPI.

**Урок.** Проверяйте гипотезу, которая объясняет **все** наблюдения. Мусор на 1,5 Мбод
в первом же захвате не объяснялся «неправильными смещениями» — это и был ключ.

## Общие выводы

1. **Проверка после каждого шага.** `cmp`, `dumpimage`, `kconfig-check`, `make info` —
   дешёвые проверки экономят часы.
2. **Код вместо догадок.** Скорость консоли, имена dtb, смещения — всё есть в исходниках.
3. **Логи — в файлы.** Сборки — в `logs/*.log`, UART — в файл с момента включения.
4. **Ресурсы.** Перед долгой сборкой — `df -h` и `free -h`.
5. **Осторожность с необратимым.** Запись на карту — с проверками; изменения SPI — только
   с бэкапом; убийство процессов — по PID.
