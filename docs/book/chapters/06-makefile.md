# Верхний Makefile

Makefile SDK — это «дирижёр»: он ничего не компилирует сам, а вызывает make
компонентов с правильными параметрами. Разберём его по частям. Полный текст — в
приложении D.

## Шапка и глобальные переменные

{{include Makefile 1-21}}

- `SDK_DIR` вычисляется из пути к самому Makefile, поэтому `make -C ~/linux-sdk`
  работает из любого каталога.
- `?=` — «присвоить, если ещё не задано». Значение можно переопределить из командной
  строки (`make JOBS=4`) или из окружения.
- `.DEFAULT_GOAL := all` — что делает голый `make`.

### Зачем `MAKEOVERRIDES :=`

Переменные, переданные в командной строке (`make FW=oga JOBS=8`), GNU make передаёт
**всем вложенным make** через `MAKEFLAGS`. То есть `make -C src/linux ...` тоже
получил бы `FW=oga` и `JOBS=8`. Пока имена не совпадают — не страшно, но если вы
назовёте переменную так же, как она называется в Kbuild (`O`, `V`, `ARCH`…),
сборка ядра сломается самым загадочным образом. `MAKEOVERRIDES :=` обнуляет список
переменных командной строки для вложенных make. Всё нужное компонентам передаётся
явно (`CROSS_COMPILE=...`, `O=...`).

## Выбор прошивки

{{include Makefile 23-48}}

1. `FW` берётся из командной строки или из файла `output/.fw`.
2. `OUT`, `IMAGES_DIR`, `LINUX_INSTALL` определяются **до** `include`, чтобы конфиг
   прошивки мог ими пользоваться.
3. Конфиг подключается, только если в целях нет `*_defconfig` (иначе при первом
   `make oga_defconfig` подключать было бы нечего).
4. Цели `oga_defconfig`, `bbb_defconfig`… создаются автоматически по файлам в
   `configs/` через **static pattern rule** `$(FW_DEFCONFIGS): %_defconfig:`.

!!! warning "Ловушка: `unexport` создаёт пустую переменную"
    В первой версии стояло `unexport FW` перед `FW ?= ...`. В GNU make 4.4 `unexport`
    **определяет** переменную (пустой), и `?=` её уже не трогает: `FW` всегда была
    пустой, а `make info` говорил «No firmware config selected», хотя `output/.fw`
    содержал `oga`. Нашлось через `make -p info | grep '^FW'`, которое показало
    `# makefile (from 'Makefile', line 20)` — строку с `unexport`.

!!! warning "Ловушка: слишком широкий шаблон"
    Первая версия правила была просто `%_defconfig:`. Но defconfig Buildroot —
    путь вида `.../configs/oga_defconfig` — тоже совпадает с шаблоном и стоит
    в зависимостях. Static pattern rule со списком из `configs/` ограничивает
    правило только конфигами прошивок.

## Пути

{{include Makefile 50-70}}

- `sdkpath` делает путь абсолютным относительно корня SDK, если он ещё не абсолютный.
- `cfgpath` различает «имя defconfig из дерева» и «путь к файлу» по наличию `/`.
- `sdkpath-pairs` нужна для списков вида `файл@сектор` и `источник:имя`: путь
  делается абсолютным, а суффикс сохраняется.

Все пути становятся абсолютными, потому что вложенные make запускаются с `-C` в
другом каталоге, и относительный путь там значил бы другое.

## Kconfig-помощники

{{include Makefile 72-98}}

### Когда пересоздавать `.config`

`.config` компонента — это файл-цель make с зависимостями: defconfig-файл и
фрагменты. Если любой из них новее `.config`, make пересоздаст его. Но есть
тонкость: если вы **поменяли имя** defconfig в конфиге прошивки (например,
`omap2plus_defconfig` → `multi_v7_defconfig`), файлов, которые бы обновились, нет.

Для этого `inputs-stamp` пишет список входов в файл `.sdk-inputs` и переписывает его
**только если список изменился**. `.config` зависит от `.sdk-inputs`, поэтому смена
списка тоже вызывает пересборку конфигурации. Вызов стоит прямо в теле Makefile
(через `$(shell ...)`) и выполняется при каждом разборе.

!!! note "Компромисс"
    Изменения из `menuconfig` живут, пока не поменялся вход. Потом `.config`
    перегенерируется, и изменения пропадут. Это осознанное правило (так же устроен
    Buildroot): постоянные изменения должны жить во фрагменте или defconfig-файле.
    Для этого есть `*-savedefconfig`.

### kconfig-check.sh

{{include scripts/kconfig-check.sh}}

Скрипт проходит по строкам фрагмента. Для `CONFIG_X=...` проверяет, что точно такая
же строка есть в `.config`; для `# CONFIG_X is not set` — что опция не включена.
Если нет — печатает, что просили и что получилось. Это и поймало панель OGA и VC4
на Raspberry Pi 4.

## Компоненты

### TF-A

{{include Makefile 110-124}}

TF-A — не Kconfig-проект, параметры передаются переменными: `PLAT` (платформа),
`BUILD_BASE` (аналог `O=`), `CROSS_COMPILE`. Цель `bl31` собирает только BL31.

### U-Boot

{{include Makefile 126-171}}

- `UBOOT_BL31` может быть `tf-a` (собрать из исходников и взять результат), путём к
  готовому ELF или пустым (платам без TF-A).
- `UBOOT_IMAGES` — какие файлы забрать из каталога сборки в `images/`: у OGA это
  `u-boot-rockchip.bin`, у BBB — `MLO` и `u-boot.img`, у RPi — `u-boot.bin`.
- `RK_LEGACY` включает дополнительную упаковку для заводского загрузчика OGA (глава 12).

### Блобы прошивки

{{include Makefile 173-188}}

Для Raspberry Pi нужны закрытые файлы прошивки GPU. Цель `bootfw` скачивает их
по URL в кэш `dl/<BOOTFW_NAME>/`, сверяет sha256 и копирует в `images/`.

### Linux

{{include Makefile 190-221}}

- `ARCH` и имя образа (`Image`/`zImage`) берутся из конфига прошивки.
- Собираются только нужные `.dtb` из `LINUX_DTBS`, а не все тысячи.
- `modules_install` с `INSTALL_MOD_PATH` кладёт модули в
  `linux-install/modules/lib/modules/<версия>/` и запускает `depmod`.
  `INSTALL_MOD_STRIP=1` вырезает отладочную информацию — модули становятся в разы меньше.

### Buildroot

{{include Makefile 223-263}}

- Buildroot не любит, когда его вызывают с чужими переменными, поэтому `BR2_DL_DIR`
  передаётся через окружение (префикс перед `$(MAKE)`).
- `make defconfig BR2_DEFCONFIG=<путь>` разворачивает defconfig из произвольного места
  и запоминает путь — потом `savedefconfig` запишет изменения **обратно в этот файл**.
- `rootfs-make BR=<цель>` даёт доступ к любой цели Buildroot, например
  `busybox-menuconfig`, `linux-headers-rebuild`, `<пакет>-dirclean`.

## Образ и прошивка карты

{{include Makefile 265-300}}

Makefile только передаёт переменные в `mkimage.sh` через окружение (глава 10).
`all` сначала собирает компоненты, потом вызывает себя же для `image` — так `image`
гарантированно запускается после всех компонентов, даже при `make -j`.

!!! example "Упражнение"
    Добавьте цель `image-xz`, которая после `image` сжимает образ
    (`xz -T0 -k images/<fw>.img`). Подумайте, от чего она должна зависеть и как
    не пересжимать образ, если он не менялся.
