# Отправная точка: разбор прошлых попыток

Хороший SDK начинается не с кода, а с инвентаризации: что уже есть, что работало,
что нет и почему. В каталоге `~/Documents/Odroid` лежали шесть экспериментов.

## Что было в каталоге

| Каталог | Что внутри | Вывод |
|---|---|---|
| `Kernel_test/linux` | клон torvalds/linux, v7.2-rc5, собран `Image` | mainline-ядро собирается |
| `Kernel_test/SD`, `NewSD` | файлы с карты EmuELEC: `boot.ini`, `extlinux/*.conf`, dtb | ядро грузилось **загрузчиком Hardkernel** |
| `Buildroot_test` | Buildroot 2026.05.1, `rootfs.ext4` | rootfs собирается |
| `Uboot_test0` | U-Boot от Hardkernel + Linaro GCC 6.3 в Docker | старый вендорский загрузчик |
| `u-boot_test_2`, `u-boot-test` | тот же U-Boot Hardkernel, свой форк | U-Boot Hardkernel, консоль была |
| `u-boot_test_mainline` | U-Boot v2026.07 (архив), rkbin, `sdmap.txt` | mainline-загрузчик собран, но **не грузился** |

Из этого сразу видно главное: ядро и rootfs собирались и работали, но запускал их
вендорский U-Boot от Hardkernel с карты EmuELEC (через `boot.ini` и `sysboot`).
Mainline U-Boot был собран — в каталоге лежал готовый `u-boot-rockchip.bin` — но
загрузиться не смог.

## Как искать причину по следам

Две вещи дали больше всего информации: история shell и файл `sdmap.txt`.

### История команд

`grep` по `~/.bash_history` нашёл, как загрузчик писали на карту:

```bash
sudo dd if=u-boot-rockchip.bin of=/dev/sda bs=512 seek=0 ...
sudo dd if=idbloader.img of=/dev/sda bs=512 seek=64 ...
sudo dd if=u-boot.itb of=/dev/sda bs=512 seek=2048 ...
sudo dd if=u-boot.itb of=/dev/sda bs=512 seek=16384 ...
sudo dd if=trust.img of=/dev/sda bs=512 seek=4096 ...
```

Видно, что пробовались разные смещения. Для mainline-U-Boot на Rockchip правильно
только одно из двух:

- либо `u-boot-rockchip.bin` целиком с **сектора 64**;
- либо `idbloader.img` с сектора 64 и `u-boot.itb` с сектора **16384** (значение
  `CONFIG_SYS_MMCSD_RAW_MODE_U_BOOT_SECTOR=0x4000` по умолчанию).

`seek=0` перетирает таблицу разделов и кладёт idbloader не туда, где его ищет BootROM.
`seek=2048` для `u-boot.itb` не совпадает с тем, где его ищет SPL.

### Карта разделов

```text
label: gpt
/dev/sda1 : start=2048,  size=2048,    name="uboot"
/dev/sda2 : start=4096,  size=4096,    name="trust"
/dev/sda3 : start=8192,  size=20480,   name="boot"
/dev/sda4 : start=28672, size=1048576, name="rootfs"
```

Раздел `boot` занимает сектора 8192–28671 и **перекрывает сектор 16384**, где SPL
ищет `u-boot.itb`. Стоит отформатировать такой раздел — и загрузчик стёрт.

Кроме того, это **GPT**. Таблица GPT занимает сектора 1–33, а на Rockchip
`CONFIG_ENV_OFFSET=0x4000` — окружение U-Boot хранится с 16 КиБ (сектора 32–63).
Сектора 32–33 общие: `saveenv` испортит таблицу разделов, а таблица — окружение.

!!! note "Вывод на тот момент"
    Похоже, проблема в раскладке: разные смещения и раздел поверх `u-boot.itb`.
    Это была правильная, но **неполная** гипотеза: в главе 11 выяснится, что даже
    с идеальной раскладкой mainline-загрузчик с SD на этой консоли не стартует вообще.

## Что взять с собой

| Что | Откуда | Как |
|---|---|---|
| Ядро | `Kernel_test/linux` (git, полная история) | локальный `git clone`, затем дотянуть тег из upstream |
| Кэш загрузок Buildroot | `Buildroot_test/.../dl` | скопировать в `dl/`, чтобы не качать заново |
| BL31 от Rockchip | `rkbin-master` | как запасной вариант к mainline TF-A |
| `loaderimage`, `trust_merger` | `rkbin-master/tools` | понадобились позже (глава 12) |
| Знания о загрузчике Hardkernel | форк `odroid-u-boot` | `build_recovery.sh` раскрыл тайну SPI (глава 11) |

Остальное (архивы, собранные деревья, старый тулчейн Linaro GCC 6.3) в новом SDK
не нужно: всё берётся из upstream свежих версий.

!!! tip "Совет: прежде чем переписывать — прочитайте свои следы"
    `~/.bash_history`, файлы `*.txt` рядом с экспериментами, `git log` в форках и
    `.config` собранных деревьев — это бесплатный журнал того, что уже пробовали.
    `grep -E 'dd if|seek=|BL31' ~/.bash_history` за секунду показал всю историю
    попыток записать загрузчик.

## Требования к SDK

Сформулируем, что должно получиться:

1. **Независимые компоненты.** TF-A, U-Boot, Linux, Buildroot — каждый в своём
   git-репозитории (сабмодуле), со своей веткой для изменений.
2. **Out-of-tree.** Сборка не пишет в исходники.
3. **Конфиги прошивок.** Один файл описывает, какие defconfig и фрагменты брать для
   каждого компонента и как разметить SD-карту. Несколько прошивок сосуществуют.
4. **Склейка.** После сборки компонентов одна команда собирает `.img`.
5. **Mainline.** Официальные версии проектов. Бинарные блобы — только там, где без
   них нельзя, и с явной пометкой.
6. **Без root для сборки.** `sudo` нужен только для записи на карту.
