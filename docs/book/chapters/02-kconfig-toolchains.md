# Kconfig, device tree и тулчейны

Три вещи, без которых нельзя ни собрать компоненты, ни понять, почему что-то
собралось не так: система конфигурации Kconfig, device tree и кросс-компилятор.

## Kconfig

Linux, U-Boot и Buildroot используют одну и ту же систему конфигурации — **Kconfig**.
Тысячи опций описаны в файлах `Kconfig` с зависимостями между ними, а выбранная
конфигурация хранится в файле `.config`.

### Файлы и команды

| Что | Зачем |
|---|---|
| `Kconfig` | описание опций: тип, зависимости, значения по умолчанию |
| `.config` | **полная** текущая конфигурация (тысячи строк) |
| `defconfig` | **минимальная** конфигурация: только отличия от значений по умолчанию |
| `make <name>_defconfig` | развернуть defconfig из дерева исходников в `.config` |
| `make olddefconfig` | дополнить существующий `.config` значениями по умолчанию для новых опций |
| `make menuconfig` | интерактивно поменять опции |
| `make savedefconfig` | свернуть `.config` обратно в минимальный `defconfig` |

Defconfig — это то, что хранят в git. `.config` — то, что реально используется при
сборке. Defconfig короткий и читаемый, но из-за значений по умолчанию одна и та же
строка в defconfig может дать разный `.config` в разных версиях исходников.

### Типы опций

- `bool` — `y` или не задана;
- `tristate` — `y` (встроено в ядро), `m` (модуль) или не задана;
- `string`, `int`, `hex` — значения.

Неустановленная опция записывается в `.config` как комментарий:
`# CONFIG_FOO is not set`.

### Зависимости и «тихое» понижение

Самое коварное в Kconfig — **зависимости ограничивают значение**. Если опция `A`
объявлена как `depends on B`, а `B=m`, то `A` не может быть `y` — максимум `m`.
Если вы попросите `A=y`, Kconfig **молча** поставит `A=m` и ничего не скажет.

Это случилось в проекте дважды:

```text
WARNING: oga.config: requested CONFIG_DRM_PANEL_ELIDA_KD35T133=y, got: ...=m
```

Драйвер панели зависит от `BACKLIGHT_CLASS_DEVICE`, который в arm64 `defconfig`
стоит `=m`. Пока не попросили `BACKLIGHT_CLASS_DEVICE=y`, панель оставалась модулем.

```text
WARNING: rpi4.config: requested CONFIG_DRM_VC4=y, got: CONFIG_DRM_VC4=m
WARNING: rpi4.config: requested CONFIG_SND=y, got: CONFIG_SND=m
```

`DRM_VC4` объявлен как `depends on SND && SND_SOC`, а `SND` зависит от `SOUND`,
который был `=m`. Цепочка: `SOUND=m` → `SND≤m` → `DRM_VC4≤m`. Решение — поднять
всю цепочку: `CONFIG_SOUND=y`, `CONFIG_SND=y`, `CONFIG_SND_SOC=y`.

!!! tip "Как найти, кто ограничивает опцию"
    Откройте `make menuconfig`, нажмите `/` и введите имя опции. Menuconfig покажет
    строку `Depends on:` с текущими значениями всех зависимостей, например
    `Depends on: ... && SND [=m] && SND_SOC [=m]`. Ищите зависимость со значением `m`
    или `n`. Тот же текст можно найти и прямо в файле `Kconfig`:
    `grep -n -A8 '^config DRM_VC4$' drivers/gpu/drm/vc4/Kconfig`.

### Фрагменты конфигурации

Хранить полный defconfig ядра для своей платы неудобно: в нём сотни строк, и при
обновлении ядра его придётся сливать с изменениями upstream. Удобнее взять **готовый
defconfig из дерева исходников** и наложить поверх **фрагмент** — короткий файл
только с вашими изменениями:

```text
# board/oga/linux/oga.config (фрагмент)
CONFIG_LOCALVERSION="-oga"
CONFIG_DRM=y
CONFIG_DRM_ROCKCHIP=y
CONFIG_JOYSTICK_ADC=y
```

Слияние делает скрипт `scripts/kconfig/merge_config.sh`, который есть и в ядре,
и в U-Boot:

```bash
make O=out defconfig                                         # база
scripts/kconfig/merge_config.sh -m -O out out/.config frag.config
make O=out olddefconfig                                      # дорешать зависимости
```

Ключ `-m` значит «только слить файлы, не запускать make». После слияния обязательно
нужен `olddefconfig`, который пересчитает зависимости, и вот тут-то опции могут
«понизиться». Поэтому в SDK после каждого слияния запускается
`scripts/kconfig-check.sh`, который сравнивает фрагмент с итоговым `.config` и
печатает предупреждение для каждой опции, которая не получила запрошенного
значения (глава 6).

### Out-of-tree сборка

И ядро, и U-Boot умеют собираться **вне дерева исходников**: `make O=<каталог>`.
Все объектные файлы, `.config` и результаты складываются в `<каталог>`, а исходники
остаются чистыми. Это ключевое требование SDK: исходники — это git-репозитории, куда
вы вносите изменения, и мусор от сборки в них не нужен. Кроме того, из одного дерева
исходников можно параллельно собирать несколько конфигураций (для разных плат).

!!! warning "Ловушка"
    Если в дереве исходников уже был собран `.config` (сборка «на месте»), ядро
    откажется собираться с `O=` и попросит `make mrproper`. Клонируйте исходники
    заново или очистите дерево, прежде чем переходить на out-of-tree.

## Device tree подробнее

Исходник `.dts` описывает плату, `.dtsi` — общие части (SoC, семейство плат),
которые включаются через `#include`. Например, для OGA:

```text
rk3326-odroid-go2-v11.dts      Black Edition (rev 1.1)
  └─ #include "rk3326-odroid-go.dtsi"   общее для OGA/OGS
       └─ #include "rk3326.dtsi" → "px30.dtsi"   SoC
```

Несколько полезных узлов, на которые мы будем смотреть:

```dts
aliases {
    mmc0 = &sdmmc;          /* SD-карта станет mmcblk0 */
};
chosen {
    stdout-path = "serial2:115200n8";   /* консоль: UART2, 115200 */
};
```

- `aliases` задаёт номера устройств. Если для SD-карты нет алиаса, её номер `mmcblkN`
  зависит от порядка инициализации — поэтому в главе 13 пришлось монтировать `/boot`
  по метке, а не по имени устройства.
- `chosen/stdout-path` говорит, куда печатать консоль и на какой скорости. Его читает
  не только ядро, но и U-Boot, и даже TF-A на Rockchip.

В mainline-ядре 7.x `.dts` лежат по каталогам производителей:
`arch/arm64/boot/dts/rockchip/`, `arch/arm/boot/dts/ti/omap/`,
`arch/arm/boot/dts/broadcom/`. Отдельный `.dtb` собирается так:

```bash
make ARCH=arm64 O=out rockchip/rk3326-odroid-go2-v11.dtb
```

## Тулчейны

**Кросс-компилятор** работает на ПК (x86_64), а код генерирует для ARM. Его имя
начинается с **префикса** (triplet), который передаётся сборкам через переменную
`CROSS_COMPILE`:

| Префикс | Для чего |
|---|---|
| `aarch64-linux-gnu-` | 64-битный ARM (OGA, Raspberry Pi 4) |
| `arm-linux-gnueabihf-` | 32-битный ARM с аппаратной плавающей точкой (BBB, Raspberry Pi 1) |

`make CROSS_COMPILE=aarch64-linux-gnu-` значит, что вместо `gcc` будет вызван
`aarch64-linux-gnu-gcc`, вместо `ld` — `aarch64-linux-gnu-ld` и так далее.

В SDK используются **два вида** тулчейнов:

1. **Системный** (`sudo apt install gcc-aarch64-linux-gnu gcc-arm-linux-gnueabihf`) —
   для TF-A, U-Boot и ядра. Им не нужна стандартная библиотека C, так что подходит
   любой свежий GCC.
2. **Buildroot-тулчейн** — Buildroot собирает его сам вместе с glibc для rootfs.
   Им же собираются все программы в rootfs. Его можно упаковать для разработки
   приложений (`make rootfs-sdk`, глава 9).

!!! note "Почему не один тулчейн на всё"
    Можно и ядро собирать Buildroot-тулчейном. Но тогда сборка ядра будет зависеть от
    сборки rootfs (сначала нужно собрать тулчейн — это 30–60 минут), а компоненты
    перестанут быть независимыми. Системный тулчейн ставится за минуту.

!!! warning "Ловушка: `arm-none-eabi-gcc` — не то"
    Тулчейн `arm-none-eabi-` предназначен для «голого железа» (микроконтроллеров) без
    ОС. Для ядра и U-Boot Linux-систем берите `arm-linux-gnueabihf-`. На хосте в этом
    проекте поначалу был только `arm-none-eabi-gcc`, поэтому для BBB и RPi 1 пришлось
    ставить `gcc-arm-linux-gnueabihf`.

### Целевой процессор

Для rootfs важно указать точное ядро CPU, чтобы компилятор использовал его
инструкции и тюнинг:

| Плата | SoC | CPU | Buildroot |
|---|---|---|---|
| OGA | RK3326 | Cortex-A35 | `BR2_cortex_a35=y` |
| BeagleBone Black | AM335x | Cortex-A8 + NEON | `BR2_cortex_a8=y`, `BR2_ARM_FPU_NEON=y` |
| Raspberry Pi 1 | BCM2835 | ARM1176JZF-S (ARMv6) | `BR2_arm1176jzf_s=y` |
| Raspberry Pi 4/400 | BCM2711 | Cortex-A72 | `BR2_cortex_a72=y` |

!!! example "Упражнение"
    В прошлой попытке в Buildroot был указан `BR2_cortex_a53`. Найдите в документации
    RK3326, какие ядра в нём стоят, и объясните, почему код для A53 на A35 всё равно
    работает, но это не лучший выбор. (Подсказка: оба — ARMv8-A, но микроархитектура
    и оптимальное расписание инструкций разные.)
